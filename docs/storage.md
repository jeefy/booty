# Storage: Release Layout, Retention and the Storage Page

What the data directory holds, which releases are kept and why, and how to free space.

## Storage

Booty's data directory is mostly releases, and it keeps more than one of each OS on purpose. `GET /storage` and the **Storage** page (which replaced the OCI Cache page) show what is there and why:

```json
{"dataDir":"/data","total":{"bytes":922865401856},"free":{"bytes":85595840512},"used":{"bytes":6658392064},
 "os":{"flatcar":{"tracked":true,"channel":"stable","pin":"","bytes":496828416,
         "releases":[{"version":"4757.2.0","bytes":496828416,"files":3,"modified":"2026-09-28T23:34:11Z",
                      "links":["current","lastGood"],"hosts":{"running":["aa:bb:cc:dd:ee:03"],"pinned":[]},
                      "retained":"current","cached":true}]},
       "coreos":{"tracked":false,"channel":"none","pin":"","bytes":2147483648,"releases":[…]},
       "bluefin":{"tracked":true,"channel":"","pin":"","source":"projectbluefin/server","bytes":3972792320,"releases":[…]}},
 "assets":[{"name":"ipxe.efi","bytes":1152512,"modified":"2026-09-28T10:01:00Z","kind":"ipxe"},
           {"name":"version.txt","bytes":169,"modified":"2026-09-25T16:18:00Z","kind":"other"}, …],
 "other":[{"name":"config","bytes":4096}],
 "autopilot":{"stateBytes":8192,"reportsBytes":20480},
 "computedAt":"2026-10-03T21:30:00Z"}
```

* `total`/`free` are the filesystem's (`statfs` on the data directory); `used` is what Booty itself holds there. Sizes come from a walk of the directory that is memoized for a minute and dropped early when a release lands or a prune runs, so the endpoint stays cheap; links, hosts and retention are joined on every request.
* **What is kept and why.** Every release directory under `data/<os>/<version>/` is listed with its size, the newest file's time, the links that name it (`current`, `previous`, `lastGood`), the hosts that reported it `running` and the hosts whose `targetVersion` pins it, and `retained`: the first reason that applies, in the order `current`, `previous`, `lastGood`, `pinned` (a configured `--flatcarVersion`/`--bluefinVersion` pin or a host's `targetVersion`), `held` (the autopilot's fleet hold), `netboot` (a host's `netbootVersion`) and `demoted` (stopped being `current` less than an hour ago), or `-` when nothing references it any more (the next sync of that OS prunes it). The page and pruning use the same rule, see [Releases and retention](#releases-and-retention-p1): Booty never keeps a release that nothing names, and never deletes one that something does. `cached:false` marks a directory that is on disk but ignored because its OS is not tracked (below). The page shows what is on disk by default. The autopilot's release records (from `GET /autopilot?releases=all`, so the whole history is there, folded or not, see [Release history](autopilot.md#release-history)) are joined in for their state badge, and a record whose files were pruned is hidden unless **Show pruned release history** (a switch in the page header with the count, remembered in the browser as `booty.storage.showPruned`) is on -- each OS card then notes `N older releases known to the autopilot, files pruned -- show` instead. A quarantined or TIMEOUT record is shown regardless, muted and marked *files pruned*, because it still keeps hosts off that release.
* **Assets** are the top-level files that belong to no release: the embedded iPXE binaries copied into the directory for DHCP setups that point at them (`kind: ipxe`), signed shims (`shim`), GRUB (`grub`) and syslinux (`syslinux`) if you put any there, and Booty's own small state (`version.txt`, `flatcar_pin.txt`, `hardware.json`, the CoreOS streams JSON; `other`). `other` sums any other top-level directory (`config/`, `cluster/`, `secureboot/`, a `registry/` left by an older Booty); `autopilot` is the controller's `state.json` and its rendered reports.
* **Freeing space.** Three releases per OS is the design; to hold less, clear hosts' `targetVersion` pins you no longer need (a pinned release is never pruned) or stop tracking an OS you do not boot: `--coreOSChannel=none` or `--flatcarChannel=none` skips its version checks and downloads, answers `/update-check` and `/info` as if no release were cached, serves an already registered host of that OS a refusal menu, and refuses new registrations of it with `400 coreos is not tracked by this Booty (--coreOSChannel=none)`. Its directory is left alone and still listed (`tracked:false`, `retained:"-"`) so you can delete it by hand. Bluefin has no channel; `--bluefinVersion` pins one release and the retention rule keeps at most three.

The OCI image cache that mirrored hosts' `ostreeImage` into an embedded registry (`/registry`, `/v2/`, `data/registry/`) is gone: hosts rebase from their own registry, exactly what `{{ .OSTreeImage }}` renders. On start-up an empty `data/registry/` is removed and logged once; one that still holds blobs is left with a warning that it is unused and can be deleted. `--ociGC` and `--ociGCEmpty` are accepted as deprecated no-ops for one release so an old command line still starts (each prints a deprecation line), and go away in the next.

### Releases and retention (P1)

Every OS keeps its releases in `data/<os>/<version>/` behind three relative symlinks: `current` (the newest release, repointed atomically once it is fully on disk and verified), `previous` (the release `current` replaced, so hosts mid-boot can finish) and `lastGood` (the newest release the whole fleet was healthy on). `lastGood` is initialised to `current` once; the autopilot controller moves it, and holds the fleet target at it after a failure (see [Autopilot](autopilot.md#autopilot)). **Pruning keeps exactly the releases that are named by `current`, `previous`, `lastGood`, a configured pin (`--flatcarVersion`/`--bluefinVersion`), the autopilot's fleet hold, any registered host's `targetVersion` or `netbootVersion` (the release a Bluefin host last netbooted, whose checksum files it is still being served), or that stopped being `current` less than an hour ago** (a grace window so hosts mid-boot into the old `current` can finish; the window is kept in memory, so a restart shortens it) -- and removes every other release directory. A bad release can be rolled back to `lastGood` without a download, at the cost of up to three releases on disk per OS (roughly 1.2 GB Flatcar, 3 GB CoreOS, 2.5 GB Bluefin).

A new release is verified before `current` moves: Flatcar against its `.DIGESTS`, CoreOS against the digests in its streams JSON, Bluefin against its `SHA256SUMS` (and its signature with `--bluefinKeyring`). When the checksums or digests themselves cannot be fetched (after three tries) the sync refuses to install the release and the served release stays where it was -- there is no fallback to an unverified download.

Booty migrates older data directories on start-up, idempotently and logged as `… release layout migrated`: Flatcar's top-level `flatcar_production_pxe.vmlinuz`/`flatcar_production_pxe_image.cpio.gz` (plain files from the earliest releases, or symlinks into `flatcar/<version>/`) end up in `flatcar/<version>/` with `current` pointing at the version from `version.txt`; CoreOS's flat `fedora-coreos-<version>-live-*` files move into `coreos/<version>/`; Bluefin's `bluefin/<version>/` with `current`/`previous` only gains `lastGood`. `flatcar_pin.txt` and `version.txt` stay where they are. The top-level names remain as symlinks into `<os>/current` (`data/flatcar_production_pxe.vmlinuz -> flatcar/current/flatcar_production_pxe.vmlinuz`), so `/data/<old name>` keeps serving the current release; `/data/<os>/<version>/…` serves any retained one.

### Per-host `targetVersion` (P1)

Each host may carry `targetVersion` (`/register`, `/hosts`, `/booty.json`): empty, or a cached release of the host's OS (`400` otherwise, naming the cached ones). Every render honours it: a Flatcar host's `/booty.ipxe` fetches `data/flatcar/<version>/…`, a CoreOS host's `data/coreos/<version>/…` with `VERSION` set to it, and a Bluefin host's `/bluefin/<mac>/` directory serves that release's netboot UKI, DDI, `SHA256SUMS`, BIOS `.linux`/`.initrd`/`.ucode` sections and a node Ignition whose sysexts, kubeadm sysext and install unit name it (the chainload and BIOS menus show its version). A `targetVersion` that has since been pruned falls back to the fleet target with a warning in the log. `/update-check` answers from the same effective target, so setting `targetVersion` on a host is how you hold it on, or move it to, a specific release: kured drains and reboots it, and it comes back running that release.
