# Power: per-host power state, Wake-on-LAN, reboot and shutdown

Booty knows whether each host is up, keeps a small state machine per host
from the signals it already records plus an active TCP probe, and gives the
operator three buttons: **Power on** (Wake-on-LAN magic packet), **Reboot**
and **Shutdown** (drain, then `systemctl reboot|poweroff` over SSH or a
privileged Pod). No BMC is involved: this is what a LAN with no IPMI can do.

## Decisions (user, 2026-09-30)

| Topic | Decision |
|---|---|
| Auth | None. The LAN boundary is trusted; every mutating endpoint Booty has (`/register`, `/flatcar/pin`, `/autopilot/.../clear`) is already open. Documented as such. |
| Reboot path | Operator reboots **never** go through kured: its sentinel means "in the next window", a button means now. SSH when `--rebootSSHKey` is set, else the API `node-reboot` Pod, else 409 "no actuator". |
| Drain | Through the k8s client when one is reachable (`API.Drain`: skip DaemonSets, honour PDBs, `--autopilotDrainTimeout`). Default on; `drain:false` skips it. |
| Cordon after shutdown | The node **stays cordoned** while off; it is uncordoned when the host reports `/booted` again. A reboot is uncordoned on `/booted` too, with a 15 min give-up that leaves it cordoned and says so. |
| Autopilot | A host that was shut down **by request** is excluded from the autopilot (no episode, no `hung`/`needs-hands`, not counted for `lastGood`). A host the autopilot is driving (`rolling|gating|retrying|rolled-back`) cannot be rebooted or shut down from the button (409). |
| WoL arming | New `--builtin` toggle `wol` (default on): `/etc/systemd/network/10-booty-wol.link` with `WakeOnLan=magic` for the host's MAC, in the Flatcar/CoreOS fragment and the Bluefin node Ignition. |
| Guards | Refuse `role: control-plane` and the last Ready worker unless `force`. |

## Facts the design rests on

- Booty already sees a host at four moments: kernel/UKI fetch (`/booty.ipxe`,
  the Bluefin UKI), Ignition fetch (`/ignition.json`, `bluefin-node.ign`),
  `POST /booted`, `POST /health`, and every 10 minutes `GET /update-check`.
  Those are the autopilot's L0/L1 signals; the power tracker reads the same
  calls from the same handlers.
- The homelab Flatcar NICs report `Supports Wake-on: pumbg, Wake-on: d`: WoL
  is supported but **disarmed** at every boot, so a node must arm it itself.
  Bluefin has no `ethtool`; `.link` files are the only portable way, and
  systemd-udevd applies `/etc/systemd/network/*.link` on the `add` event the
  real root's `systemd-udev-trigger.service` re-issues for every NIC after
  the switch-root, on Flatcar, CoreOS and Bluefin alike (udev's
  `net_setup_link` builtin, not networkd, applies `[Link]`; it works whether
  the host runs networkd or NetworkManager). `/etc` is writable on all three
  (Bluefin's erofs image is `/usr`; `/etc` is an overlay). Should a Bluefin
  image ever ship an immutable `/etc/systemd/network`, the fallback is a
  oneshot `ethtool -s <if> wol g` — which that image would also have to carry
  `ethtool` for; today it does not, so the `.link` file is the plan.
- A magic packet is 6 × `0xFF` followed by the MAC 16 times, UDP to port 9
  (or 7). It must reach the host's L2 segment: Booty sends it to the
  broadcast address of every non-loopback IPv4 interface it has, to
  `255.255.255.255`, and unicast to the host's last known IP (the switch may
  still hold the MAC in its table). Firmware must have WoL enabled in BIOS
  too; Booty cannot see that, so "did not wake" is an event, not an error.
- An operator cannot be sure a reboot happened just because `systemctl
  reboot` returned 0; the tracker treats the request as an **expectation**
  with a window (10 min reboot / 5 min shutdown / 10 min power-on) and
  resolves it from the signals, so the UI never shows `rebooting` forever.
- `kured`'s actuator semantics (sentinel + next window) are wrong for a
  button. The autopilot's `Chooser` keeps its order; the power manager asks
  it for the **operator** actuator (SSH, API, none) explicitly.

## Out of scope

BMC/IPMI/Redfish; scheduled power (cron); fleet-wide actions; authentication
(see Decisions); Secure Boot or installed-mode Bluefin specifics (the
tracker treats every host the same); power metering.

## State model

Per host, on the hardware record as `power` (persisted in `hardware.json`,
served by `/hosts`, `/booty.json`, `/power`):

```json
"power": {
  "state": "up",
  "since": "2026-09-30T10:00:00Z",
  "reason": "probe ok (22)",
  "request": "reboot",
  "requestedBy": "192.168.1.20",
  "requestedAt": "2026-09-30T09:58:00Z",
  "lastSeen": "2026-09-30T09:57:12Z",
  "cordoned": true,
  "probe": {"ok": true, "at": "2026-09-30T10:00:00Z", "method": "tcp/22"}
}
```

States: `unknown` · `off` · `powering-on` · `booting` · `up` · `draining` ·
`rebooting` · `shutting-down` · `unreachable`.

`reason` is free text for the UI tooltip and never carries another host's
identity; `request` is the action in flight (or the satisfied `shutdown`
while the host is `off`); `requestedBy` is the remote address of the
operator (the host record is not a report; events carry no addresses);
`lastSeen` is the last moment any Booty-side signal or a Ready node proved
the OS up; `cordoned` remembers that Booty cordoned the node and owes it an
uncordon.

### Signals and transitions

The tracker (`pkg/power.Tracker`) recomputes every host every 30 s and
reacts to signals at once:

| Signal | From | Effect |
|---|---|---|
| kernel/UKI fetch (L0) | `handleIPXERequest`, `recordBluefinNetboot` | → `booting`. Clears a `powering-on`, `rebooting` or satisfied `shutdown` request (the host is back under its own power). |
| Ignition fetch | `recordBoot`, `serveBluefinNodeConfig` | refreshes `lastSeen`; `booting` if nothing better is known |
| `POST /booted` | `handleBootedRequest` | → `up`; owed uncordon is issued; `lastSeen` |
| `POST /health`, `GET /update-check` | their handlers | `lastSeen` refreshed; `booting|unknown|unreachable|off` → `up` (the OS answered) |
| Node Ready (k8s client) | tracker tick, one `Nodes` listing per tick | counts as seen (`lastSeen`); NotReady is not a signal on its own |
| autopilot episode `rolling|retrying|rolled-back` with a reboot requested and not yet observed (`RebootWanted`) | controller | → `rebooting` with reason `autopilot: attempt N into R`; cleared by L0 like any other |
| operator `on` | `POST /power/{mac}/on` | → `powering-on`, 10 min window |
| operator `reboot` | `POST /power/{mac}/reboot` | → `draining` while the drain runs (when one does), then `rebooting`, 10 min window from the request |
| operator `shutdown` | `POST /power/{mac}/shutdown` | → `draining`, then `shutting-down`, 5 min window |
| operator `cancel` | `POST /power/{mac}/cancel` | drops the request; state recomputed from the probe and `lastSeen` |
| active probe | tracker tick, TCP connect to the host IP on 22 then 10250, 3 s timeout each, only when the host has an IP | see below |

Probe outcomes, by current state:

| State | probe ok | probe fails |
|---|---|---|
| `unknown`, `unreachable`, `up`, `booting` | `up` | `unreachable` once nothing has been seen for **15 min** (and the probe failed); before that the state is kept |
| `off` | `up` (someone pressed the button; event "came back without a request") | stays `off` |
| `powering-on` | `up` (the OS is answering before Booty saw the kernel: a host that was only `unreachable`) | stays until L0 (`booting`) or the 10 min window → `off`, event "did not wake" |
| `rebooting` | kept (the old OS is still answering, or the new one is already up without a `/booted`); after the window: `up`, event "reboot was not observed" | kept; after the window: `unreachable` (reason says the reboot was requested) |
| `shutting-down` | kept; after the 5 min window: `up`, event "did not shut down" | → `off` (requested shutdown satisfied; `request: shutdown` stays so the autopilot keeps excluding the host) |
| `draining` | kept (the action is in flight) | kept |

No IP: no probe. The state is `up` while `lastSeen` is within 15 min, else
`unknown` (it was `booting`/`up`) — never `unreachable`, which is a probe's
word.

Hosts the tracker has never heard of start `unknown`. A probe success writes
`probe.ok/at/method` every tick but the record is persisted only when state,
reason or request changed, or `lastSeen`/`probe.at` moved by more than a
minute, so the 30 s tick does not rewrite `hardware.json` for a quiet fleet.

Events (`kind: "power"`, MAC as a field, text without hostnames, IPs or
MACs) go to the autopilot's events ring when a controller runs, and always
to the tracker's own ring of 200, which `GET /power` serves. The Autopilot
page shows both (deduplicated), with a `power` kind badge.

## Actions

`POST /power/{mac}/{on|reboot|shutdown|cancel}` with an optional JSON body
`{"reason": "...", "force": false, "drain": true}` → `202 Accepted` with the
host's new `power` block, or:

| Status | When |
|---|---|
| 400 | bad MAC, bad body |
| 404 | host not registered |
| 405 | not POST |
| 409 | another action is in flight (same action within its window: 202, idempotent); a guard refused (body says which); `no actuator: configure --rebootSSHKey or run Booty in the cluster`; action not allowed from the current state (`on` only from `off`/`unreachable`/`unknown`; `reboot`/`shutdown` only from `up`) |

### on

`power.Wake`: the magic packet to UDP 9 on the broadcast of every
non-loopback IPv4 interface Booty has, `255.255.255.255`, and unicast to
the host's IP when known; three rounds one second apart. Needs no cluster
and no actuator. The state is `powering-on` at once; the sender runs in the
background and logs (never fails the request: a send error on one interface
is normal in containers).

### reboot

Guards, in order: not `up` → 409; autopilot driving the host → 409
`autopilot is driving this host`; `role: control-plane` and not `force` →
409 (`control-plane host; set force to reboot it anyway`); no operator
actuator → 409. Then, in the background: cordon + drain through the k8s
client when `drain` (default true) and a client is reachable (the node is
resolved by hostname and confirmed by the DMI product UUID when known, as
the autopilot does; `draining` is shown meanwhile), then `systemctl reboot`
over SSH (`core`+sudo or `root`) or the `booty-node-reboot-<node>` Pod
(`/booty node-reboot`). State `rebooting`, `cordoned: true` when Booty
cordoned. On `POST /booted` the node is uncordoned (`finishActuator`-style:
through the same actuator kind, best effort, event on failure). If no
`/booted` arrives within **15 min** the node is left cordoned, `cordoned`
stays true and an event says so; the next `/booted` still uncordons it. An
actuator failure before the reboot was issued reverts the state (uncordon
if Booty cordoned) and emits an event.

### shutdown

Same guards plus: the host's node is the **last Ready worker** (cluster
client: Ready, schedulable, not control-plane; without a client: the only
registered worker that is `up`) and not `force` → 409. Drain as above, then
`systemctl poweroff` over SSH or the Pod with `/booty node-reboot
--poweroff` (SIGRTMIN+4 → `poweroff.target`). State `shutting-down`; the
probe's first failure makes it `off`. The node stays cordoned; when the
host comes back (`/booted`) it is uncordoned. While `request: shutdown` and
the state is `shutting-down`/`off`, the autopilot excludes the host:
`hostsOf` drops it, so no episode starts, nothing is `hung`, and
`fleetHealthyOn` does not wait for it. `/update-check` keeps answering as
before when it returns; the first kernel fetch clears the request.

### cancel

Clears a stuck `powering-on`/`rebooting`/`shutting-down`/`draining`
expectation. The state is recomputed from the probe and `lastSeen` on the
spot. An action still running in the background finishes but does not set
state afterwards (it checks the request token).

## Capabilities and status

`GET /power`:

```json
{
  "hosts": {"<mac>": {"state": "up", ...}},
  "events": [{"at": "...", "kind": "power", "mac": "<mac>", "text": "reboot requested: ..."}],
  "capabilities": {"wol": true, "actuator": "ssh"},
  "summary": {"up": 6, "off": 0, "unreachable": 0, "inFlight": 0}
}
```

`actuator` is the operator actuator (`ssh` when `--rebootSSHKey` is set,
`api` when a cluster client is configured and reachable, else `none`); it
is what the buttons' enablement reads. `GET /info` gains
`"power": {"up", "off", "unreachable", "inFlight"}`.

## UI

- Hosts table: a power badge (coloured dot + state + since, tooltip =
  reason) next to the hostname; the host form shows the same badge
  read-only. **Power on** / **Reboot** / **Shutdown** buttons per row,
  enabled by state: `on` from `off|unreachable|unknown`; `reboot` and
  `shutdown` from `up`; otherwise disabled with the reason in the tooltip
  (`host is <state>`, `autopilot is driving this host`, `no actuator:
  configure --rebootSSHKey or run Booty in the cluster`). Clicking opens an
  inline confirm with a reason field and, only when a guard would refuse
  (control-plane; last `up` worker), a *force* checkbox. 409s are shown on
  the row.
- Home: the Fleet card gains `6 up · 0 off · 0 unreachable` from `/info`.
- Autopilot: power events in the timeline with a `power` kind badge, also
  when the autopilot is off (from `/power`).

## Composition

`--builtin` gains `wol` (in the default). It writes
`/etc/systemd/network/10-booty-wol.link`:

```ini
[Match]
MACAddress=aa:bb:cc:dd:ee:01

[Link]
WakeOnLan=magic
```

into the Flatcar/CoreOS builtin fragment and the Bluefin node Ignition
(overwrite, like the other `/etc/booty` files). The goldens change by that
file only.

## Tests

- `pkg/power`: tracker state machine with a fake clock and a fake probe
  (unknown→up by probe; up→unreachable after 15 min of probe failures;
  off→powering-on→booting→up; powering-on → off after 10 min "did not
  wake"; shutdown→shutting-down→off; off→up without a request; rebooting →
  booting on L0 and → up after the window; cancel; no-IP hosts); WoL packet
  bytes and destinations against a local UDP listener (three rounds);
  manager guards (control-plane, last worker with and without a cluster,
  autopilot driving, no actuator, in-flight 409, idempotent 202, force),
  drain/reboot/poweroff through fake actuators, uncordon on `/booted`,
  15 min give-up, cancel.
- `pkg/autopilot/actuator`: `node-reboot --poweroff` sends SIGRTMIN+4; the
  Pod manifest carries the flag; `SSH.PowerOff` runs `systemctl poweroff`.
- `pkg/autopilot/controller`: a requested-off host starts no episode, is not
  counted by `fleetHealthyOn`, and is skipped by the rollout.
- `pkg/server`: the handlers (status codes above), `/power`, `/info.power`,
  signals reaching the tracker, `wol` builtin in the Flatcar fragment and
  the Bluefin node config, refreshed goldens.
- `web`: vitest for the buttons' enablement matrix, the confirm flow
  (reason, force only when a guard applies, 409 shown), the badge, the
  Home summary, the timeline badge.

## Open questions

- Reboot/shutdown of a host without a cluster client and without SSH: the
  reboot Pod needs the API, SSH needs a key. There is no third way without
  a BMC, and the UI says so rather than falling back to the sentinel.
- `requestedBy` is a remote address on the host record. It is not in any
  report or event; if the records are ever shared, drop it there.
- The probe is TCP-only (22, 10250). A host with neither sshd nor a kubelet
  (a brig host, a Bluefin install in progress) reads as `unreachable` once
  it has been quiet for 15 min; its 10-minute `/update-check` normally
  keeps it `up`, and a `booting`/`unknown` host is never called
  `unreachable` without a failed probe.
- The IPv4 broadcast list is read from the process's interfaces at send
  time; in a container with only the Pod network, the unicast and
  `255.255.255.255` sends are what reaches the LAN (hostNetwork is the
  deployment answer, not Booty's).
