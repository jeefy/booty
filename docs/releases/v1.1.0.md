# Booty v1.1.0 release notes

The first feature release after v1.0.0. The headline is **soak/cooldown
pacing for the autopilot** (#80): two new flags, `--autopilotSoak` and
`--autopilotCooldown`, pace how the fleet adopts releases -- canaries keep
following every release, and the rest of the fleet moves in waves, one per
cooldown, onto the newest release that soaked healthy on a canary. Skip-ahead
means several releases inside one cooldown cost one reboot per host, and the
releases passed over are marked `skipped`. Both flags default to `0`, which
reproduces 1.0.0 behaviour exactly.

The release also carries a **review-hardening pass** (#86): the container
image runs as nonroot (uid 65532) with file capabilities, downloads that
cannot be verified are refused instead of silently installed, routine
`hardware.json` bookkeeping is batched (flushed at most every 2 s and on
shutdown), and the Web UI pauses polling while its tab is hidden and backs
off on errors. The documentation was split out of the README into per-topic
pages under `docs/`. Rounding it out are dependency bumps across the Go
modules and the Web UI (#83, #87).

## Breaking changes

* **The container image runs as nonroot (uid 65532).** `USER 65532:65532`
  with a 65532-owned `/data`; the `NET_BIND_SERVICE` and `NET_RAW`
  capabilities moved to *file* capabilities on the `/booty` binary. The
  `/data` volume must be writable by uid 65532, the bounding set must still
  include the two capabilities, and the autopilot's reboot/power Pods
  (`booty node-reboot`) now run as root (`runAsUser: 0`) because the main
  image no longer does. `make image-run` maps the container to the invoking
  user so the bind-mounted `./data` stays writable.
* **Fail-closed verification.** The Flatcar, CoreOS, Secure Boot bundle and
  Flatcar CA syncs now refuse to install when the checksums or digests they
  verify against cannot be fetched (after three tries); they previously fell
  back to an unverified download. Unpinned Fedora RPMs (a non-default
  `--fedoraShimVersion`/`--fedoraGrubVersion`) are verified against the
  mirror's own repository metadata, and when the metadata cannot verify them
  the install is refused unless `--allowUnverifiedFedoraRPMs` is set.

## Upgrading from v1.0.0

* **chown the data directory to uid 65532.** The image no longer runs as
  root, so an existing data directory owned by root is not writable:

  ```
  chown -R 65532:65532 <dir>
  ```

  This is required for **hostPath** volumes in particular, because `fsGroup`
  does not apply to hostPath. Alternatively, set `runAsUser: 0` to keep
  running as root. On other volume types, `fsGroup: 65532` with
  `fsGroupChangePolicy: OnRootMismatch` plus `runAsUser: 65532` and
  `runAsNonRoot: true` works; the example in
  [examples/k8s.yaml](../examples/k8s.yaml) does all of these.
* **Set `BOOTY_IMAGE` to the same tag as the Deployment's `image:`.** The
  autopilot's API actuator schedules the reboot Pods from the image named by
  `BOOTY_IMAGE`, and the downward API cannot supply it. Keep the two in sync
  when you bump the tag.
* **Keep the capabilities as they are.** The bounding set must include
  `NET_BIND_SERVICE` and `NET_RAW`, and do **not** set
  `allowPrivilegeEscalation: false`: with `no_new_privs` the file
  capabilities are silently not granted, so the binary starts but, as
  non-root, cannot bind :67/:69/:80 or open raw sockets. Podman users need
  `--cap-add NET_RAW` (Podman's default set lacks it) together with
  `--cap-add NET_BIND_SERVICE`.
* **Unverifiable downloads are now refused.** Flatcar, CoreOS, Secure Boot
  bundle and Flatcar CA syncs fail closed when the checksums or digests they
  verify against cannot be fetched. If you pin a non-default
  `--fedoraShimVersion`/`--fedoraGrubVersion` and want the old
  fall-back behaviour for those RPMs, set `--allowUnverifiedFedoraRPMs`.
* **Startup validation is stricter.** Booty now validates the
  endpoint-override flags (`--githubAPIURL`, `--githubDownloadURL`,
  `--fedoraMirrorURL`, `--fedoraReleases`, `--coreOSStreamsURL`) and exits on
  malformed values, and `--tftpBlockSize` must be in the legal 512..65464
  range (`0` means "library default (512)"). A command line that started on
  v1.0.0 with a bad value now fails fast instead of misbehaving later.
* **Soak/cooldown defaults to off.** `--autopilotSoak` and
  `--autopilotCooldown` both default to `0`, which is exactly 1.0.0
  behaviour; opt in per fleet (the homelab setting is `24h`/`48h`).

## Verify

The container image's version comes from the tag: the workflow passes
`BOOTY_VERSION=${{ github.ref_name }}` as a build-arg, the Dockerfile turns
it into `-X main.version=${BOOTY_VERSION}`, the binary exposes it as
`/info.booty.version`, and the UI's **About** page renders that field.
Running `:v1.1.0` should show `Booty version: v1.1.0` there.

Release tags are built with SLSA level-3 provenance and a keyless cosign
signature. Verify locally with:

```
COSIGN_EXPERIMENTAL=1 cosign verify-attestation --new-bundle-format=false \
  --certificate-identity-regexp=".*" --certificate-oidc-issuer-regexp=".*" \
  --type slsaprovenance ghcr.io/jeefy/booty@<digest>
```
